## Bloco 2b: Hardening (integração com a UI)

- [x] H.1 Idempotência global (F0) nos endpoints individuais — IdempotencyMiddleware opt-in por header (POST/PUT/PATCH/DELETE, rotas auth/webhooks/support/offline excluídas); 2xx consome a chave (reuso → 422), 4xx/5xx/exception LIBERA a chave (retry com a mesma chave); adesão medida em todo tráfego de mutação; counter idempotency_key.reused; RequireKey permanece escopado ao sync-batch; 8 testes middleware + 2 Redis (ReleaseAsync)
- [x] H.3 F1 HTTP nos endpoints individuais — OptimisticRevisionMiddleware genérico por path (chave `tenant:path`): GET em escopo devolve `ETag` corrente; mutação com `If-Match` stale → 412 `{message, code: revision-conflict, currentRevision}`; 2xx INCR a revisão e devolve ETag novo; sem If-Match passa (Enforce=false) ou 428 `revision-required` (Enforce=true); guard HasStarted (não tocar header em resposta streaming); counter revision.conflict; parser aceita "5", "5-1.0.0-hash", quoted e W/; 10 testes middleware + 2 Redis (persistência entre instâncias)
- [x] H.2 Revisão da integração com a UI (modo offline) — UI usa handlers por feature (não sync-batch): chave preservada em retries ✓, 412 sem retry ✓, 422 tratado como "já processado" (M1) ✓; F1 HTTP (If-Match) implementado na UI (M2 — ver 4.6)
- [x] H.4 Reserva atômica da revisão (CAS) — a mutação com `If-Match` **reserva** a próxima revisão antes de executar o endpoint (Redis: script Lua `GET`+`INCR`; memória: `TryUpdate` em laço): dois clientes com o mesmo ETag — só um executa, o outro recebe 412 (sem CAS, ambos passariam na verificação e o último sobrescreveria o outro). Falha do endpoint → **rollback** da reserva: o cliente reenvia com o MESMO ETag (retry da fila offline). `IETagManager.TryReserveResourceRevisionAsync`/`ReleaseResourceRevisionAsync`; 3 testes middleware (conflito após sucesso, concorrência, rollback) + 4 testes Redis (CAS, stale, release, release obsoleto)
- [x] H.5 Enforcement de revisão **escopado por path** — `OfflineSync:Revision:EnforcedPaths` (lista de padrões `"MÉTODO /path/{id}"`) restringe o 428 (sem `If-Match`) às mutações cobertas pelo cliente; lista vazia = enforcement global (comportamento anterior). Sem isso, `Enforce=true` bloquearia também criações (`POST`, sem ETag possível) e upserts de collection, impedindo o rollout incremental. `RevisionEnforcementPatterns` (casamento por método + contagem de segmentos; `{id}` = 1 segmento); 7 cenários no middleware + 16 casos no matcher; UI: 428 classificado como `conflict` na fila (nunca erro permanente) e mensagem específica no caminho online (notas e fórmulas)
- [x] H.6 Métrica de adesão **por rota** (`revision.adherence`) — toda mutação HTTP em escopo é medida com tags `route` (rota normalizada: segmentos numéricos/GUID → `{id}`) e `state` (`provided` \| `wildcard` \| `missing`), permitindo decidir o rollout **por recurso** (o `revision.missing` existente só cobre o sync-batch); cardinalidade limitada (50 rotas + bucket `__other__`) contra paths arbitrários; `RevisionRouteNormalizer` + `MetricsService.RecordRevisionAdherence`; 10 casos do normalizador + 4 da métrica (nome/tags/cap/vazamento) + 6 no middleware (estados, GET e rota excluída fora da medição)
- [x] H.7 Pipeline de métricas verificado **de ponta a ponta** (smoke test Prometheus) — a verificação live na stack (API → OTLP → otel-collector → exporter prometheus :8889 → Prometheus :9090) revelou que o exporter converte o ponto em underscore **sem** sufixo `_total` (série real `revision_adherence`, não `revision_adherence_total`) — todas as queries/documentação usavam o nome errado (retornavam vazio em silêncio) e os alertas de ano letivo referenciavam `academic_year_operations_total`/`academic_years_created_total`, séries que **nunca existiram** (as regras nunca disparavam). Correções: nomes reais na documentação (contrato da API + runbook), `prometheus-academic-year-alerts.yml` corrigido, novo `prometheus-offline-sync-alerts.yml` (6 alertas, todos filtrando `environment=production|staging`: métrica ausente **por ambiente** — `OfflineSyncRevisionMetricAbsent` na produção e `OfflineSyncRevisionMetricAbsentStaging` no staging, adesão < 99% por rota, chave ausente > 1%, taxa de 412, conflitos do batch) registrado no `prometheus.yml` e montado no `docker-compose.yml` (o arquivo de billing também não era montado — suas regras não carregavam), smoke test repetível `observability/test-offline-sync-metrics.sh` (fire → export → scrape → asserção de séries/labels/alertas) e teste de guarda `PrometheusMetricNamingTests` (4 casos) que falha o build se um alerta referenciar métrica inexistente ou usar `_total` em métrica OTLP — o guard foi validado reintroduzindo o nome quebrado (falhou como esperado)
- [x] H.8 Ponte **Meter → Prometheus** no endpoint `/metrics` (caminho de produção) — a topologia real (API no Render + Prometheus local) **não tem collector OTLP**: o Prometheus scrapeia `GET /metrics` da API, e esse endpoint era servido pelo `PrometheusController`, que expunha **apenas** as gauges de analytics — as métricas do Meter (adesão, idempotência, billing, ano letivo) **não chegavam ao Prometheus de produção** (o gate do rollout ficaria sem dado) e o `app.MapMetrics()` (prometheus-net) ficava sombreado. Agora o endpoint serve as três fontes no mesmo scrape: analytics + `SchoolManagementMetricsCollector` (listener do Meter "SchoolManagement" → texto Prometheus, mesma convenção de nomes do collector: ponto → underscore, sem `_total`) + registro do prometheus-net; `MetricsMiddleware` passa a normalizar a label `route` (o path cru viraria uma série por id — cardinalidade explosiva agora que a métrica é exposta em produção); 9 casos do coletor (counter/gauge/histogram/labels/escaping/nome/sorted/isolamento de meter) + 3 do controller (compatibilidade das gauges de analytics, presença das métricas do Meter, content-type) + smoke test cobrindo os DOIS caminhos (/metrics e OTLP) — verde na stack; **corrigido o smoke test**: com `set -o pipefail`, `grep -q` em pipe grande causa SIGPIPE (141) e virava falso negativo (herestring)
